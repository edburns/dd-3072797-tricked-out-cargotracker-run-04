## Section 7: Failure Analysis

There was no terminal task failure, timeout, idle kill, CI failure, review rejection, merge conflict, or post-merge verification failure.

One recoverable command error occurred near the end of phase 1. The first atomic readiness command passed `--jq --arg` directly to `gh run list`; that `gh` version rejected `--arg` with `unknown command "head" for "gh run list"`, and the command exited `1`. The shepherd did not treat the failed mutation/check as success. It reran the gate by collecting `gh run list --json` output and applying `jq --arg` separately. The corrected gate passed with four successful checks, zero unresolved threads, and the unchanged expected head.

This did not affect repository state or final correctness, but it added a retry and demonstrates a CLI compatibility hazard. The root cause was mixing native `jq` arguments with `gh`'s `--jq` option rather than invoking `jq` as a separate process.

## Section 8: Observations and Recommendations

### What worked well

- **Fail-closed state transitions:** both readiness and merge gates asserted the exact head and base, preventing stale-review or wrong-base merges.
- **Requirement-level evidence:** phase 1 went beyond a package build and exercised the browser workflow, persistence behavior, cancellation behavior, and adjacent destination/routing paths.
- **Fast review convergence:** CCRA approved the first reviewed head with zero findings.
- **Current-head CI discipline:** all four required checks were tied to the exact reviewed head before merge.
- **Treatment integrity:** lesson propagation remained `off`, and no campaign lesson was written.
- **Persistent run metadata:** `shepherd-task-25-given-list-run.json` captured the invocation identity and successful outcome consistently.

### What could improve

- **Avoid unsupported `gh --jq` composition:** scripts should pipe JSON to standalone `jq` whenever variables such as `--arg` are required. This removes the recovered phase-1 failure.
- **Record unredacted aggregate token totals:** preserving only aggregate input/output/cache/reasoning counts would improve cost comparisons while avoiding prompt-content retention.
- **Emit structured phase summaries:** each phase should write a compact JSON outcome containing issue, PR, head, start/end, review ID, findings, checks, merge SHA, and failure signatures. The report currently reconstructs these from transcripts.
- **Separate orchestration timing:** explicit timestamps for phase launch, export, and final manifest closure would explain the 6m 34s outside captured CLI sessions without inference.
- **Normalize review terminology:** emit both `review_rounds` and `finding_count` directly. This run had one review round and zero findings; treating “comments generated” as the only review metric would obscure that successful review event.

### Recommended script/skill changes

1. Replace any `gh ... --jq --arg ...` pattern with `gh ... --json ... | jq --arg ...`.
2. Add a machine-readable `phase-outcome.json` per issue and phase.
3. Add aggregate token fields to the terminal `result` event when policy permits, even if detailed telemetry remains redacted.
4. Preserve the exact successful gate command or gate version in the phase outcome so CLI compatibility regressions can be compared across campaigns.
5. Continue requiring exact-head review, zero unresolved threads, current-head checks, immutable merge SHA capture, and post-merge issue-state verification; these controls were effective.
